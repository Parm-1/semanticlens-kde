## Blocking finding R1 — numeric group ownership can change between check and signal

backend.cpp:22-27 reads /proc/PID/stat, then calls kill(-PID,SIGKILL) separately. finish at383-387 repeats this25ms later after QProcess reports/reaps the helper. The valid interleaving is: read matching old leader (or absent leader while original descendants remain); original leader/group finally disappears; the now-free number is allocated to a different process group; numeric kill targets that new group. No old renderer must behave maliciously. The comment that Linux cannot reuse the group ID is true only while old members retain it; the read does not keep that condition true until kill.

This is a source-level race defect, not an observed host mis-signal. The Linux allocator removes the numerical ID after no task remains in any PID type; kill addresses the group currently bearing that number. See [Linux pid.c free_pid/__change_pid](https://raw.githubusercontent.com/torvalds/linux/v6.12/kernel/pid.c) and [Linux kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html). Existing start-tick checks correctly reject a new leader already present at the read, but do not protect reuse after the read. Existing sampled closure controls never exercise that interleaving. No forced PID reuse or other hostile test was run.
