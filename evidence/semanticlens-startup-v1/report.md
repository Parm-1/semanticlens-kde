# Bounded SemanticLens startup investigation v1

The original 90.032-second branding helper timeout is explained by its relative directory socket argument in the observed native Qt/service configuration. The next consumer is the parent release owner; this report supplies evidence for that owner's acceptance. No candidate source change was made or found necessary for this bounded startup result.

## Primary contract

Current CMake selects ui-v4, service-v3 and core-v5. `tools/ui_smoke.cpp:22-23` converts service/probe/models/data arguments to absolute file paths but passes socket argv[5] verbatim. Original worker invocation supplied `native-runtime/smoke.sock`, cwd `/public-clean-v2/source`. Backend forwards that string to both QLocalSocket and the detached service (`src/ui-v4/backend.cpp:167-180`). Service passes it to QLocalServer::listen and returns 2 when its second listen fails (`src/service-v3/main.cpp:64-80`), before Engine construction. Data preparation explicitly creates the directory and sets owner rwx (`:54-57`); original worker reports initial data/runtime modes 0700, matching current readback. Missing initial 0700 is not the established cause.

Original worker transport readback: readonly Arch root, writable owned source at `/public-clean-v2/source`, readonly models at `/models`, cwd `/public-clean-v2/source`; UI helper arguments `./stage/usr/bin/kde-index-service ./stage/usr/bin/embedding-probe /models native-data native-runtime/smoke.sock corpus native-output/window`. Disposable HOME/XDG paths and host Wayland were bound. The copied generic timeout and model-path receipts are retained under raw/. That timeout itself records neither Backend phase nor service error and remains insufficient alone.

## Discriminant and observations

A new observer compiles the unchanged production Backend source/header in the same readonly Arch userspace (Qt base 6.12.0-2). It calls the same constructor, logs public Backend fields and independently requests actual service status through another local socket. Exact staged service 28c0d5dd and producer fa7d1467 use the same readonly model files, six CPU threads, disposable data/runtime initially 0700 and no selected root. Candidate and predecessor artifacts stayed readonly. This is a source/model startup experiment, not a staged GUI executable or native window claim.

The negative uses original socket string `native-runtime/smoke.sock`. Backend reports disconnected, modelSetupNeeded=false, modelReady=false and actual retry-bound message at 5441ms. Terminal observation at 8541ms remains disconnected/unready. No service status reply exists; data is empty and socket absent. Process samples observe the real attempted service command with that relative socket. This retains the contradictory setup outcome instead of labeling the timeout a model-verification failure.

The positive changes only the socket argument to an absolute path under that run's owned runtime. It receives 49 actual protocol-1 status replies: 45 phase:verifying replies with both readiness fields false, four phase:ready replies with both true. Ready status binds CPU/model/runtime/pipeline/producer identities. Backend is connected, modelReady=true, message Ready at 5281ms. Inventory observes actual service and embedding producer. No indexing or vector parity was rerun. Diagnostic outer observer intervals are 10.274s negative and 6.979s positive, including polling/shutdown/closure; these are not latency/performance measurements.

A direct launch of the exact staged service with the relative socket exits 2 in 65ms. Default stderr is empty, matching the original logging limitation. A linked repeat changes only diagnostic QT_FORCE_STDERR_LOGGING=1 and fresh owned paths; exit 2 in 16ms emits the original native message `"QLocalServer::listen: Name error"`. Both direct receipts show empty data/no socket. This locates rejection before Engine bootstrap and explains why model-file presence cannot make the original socket configuration ready. These are startup controls, not four independent product experiments.

## Closure, limits and stop rule

Positive calls Backend::shutdownOwnedService after readiness. Actual disconnect makes the readiness predicate false. Generic disconnect text still says reconnecting, but shutdown stops retry. Both observer runs record no remaining scoped process, no socket and no forced live cleanup before namespace teardown. Outer bwrap returns and destroys its private PID namespace; direct service processes are reaped with exit 2. No live build/run/desktop/model/socket handle remains. No host install, personal root, Baloo/global config, model download, source repair, publication or descendants occurred. Initial readonly mount failure and corrected build invocation are retained.

Supported contract is bounded: this exact relative socket string with a directory separator fails in this Qt/service environment; an absolute private socket with existing parent passes actual startup. It does not establish that all relative/simple socket names are invalid; application default simple socket name is a distinct Qt contract. Original full UI helper remains failed; no replacement full window/index/preview claim. Existing accepted producer/lifecycle/native-label evidence is reused unchanged, with no corpus/runtime generalization.

Outcome branches: setup rejection plus corrected actual readiness -> bounded setup diagnosis; unchanged absolute configuration fails or actual failed readiness -> return candidate finding/source/repair contract to parent. First branch occurred. Stop rule is satisfied after matched negative, raw positive verifying/ready phases, direct native rejection and closure; no broad suite repeat. Parent can pass an absolute socket in future directory-path helper invocations. No acceptance criterion, production authority or source contract changed. Usage/billing and aggregate investigator elapsed time are unknown; only stated runner endpoint intervals measured.
